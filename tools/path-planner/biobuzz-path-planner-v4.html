BioBuzz Path Planner — how to use

1 · Draw paths

  • Drag on the field to draw an arrow — it queues driver.moveTo(x, y, rotation) from the current end of the path. Every arrow starts where the last step ends (the pulsing ring).
  • Curve steps generate curveTo(...): a Bezier pulled toward its control points (square handles — drag them). It does not pass through them.
  • Through steps generate throughTo(...): the robot passes through each waypoint (open circles).
  • Hold Shift to snap to a 1″ grid. Wheel = zoom, middle-drag = pan, Fit view resets. Drag the green robot box (23″ × 12″) to place the start; drag its round handle to rotate. The yellow cross is the tracked pose — the box center shifted by the pod offsets (Java code tab) — and is what setStartPose and every path use.
  • Toolbar buttons and keys (M C G R T S W) insert the new step right after the selected step (at the end when nothing is selected) — e.g. select drive 6, press S, and the code step lands between drive 6 and drive 7. The ▲▼ buttons on each list row reorder steps.

2 · Routes — several segments, ONE continuous path

  • Route (R) chains line / curve / through segments that the follower drives as a single continuous path — no stop between segments, unlike separate moves.
  • Add segments in the inspector, or drag on the field while the route is the selected last step to append straight segments.
  • Base heading and Override heading emit .heading(...) / .overrideHeading(...); per-segment headings emit .heading(...) right before their segment.

3 · Run your code anywhere along the path

  • Path callbacks — select a drive step and use Run code along the path: onStart, onProgress(fraction, …) and onComplete lambdas fire once, mid-drive, via Options — the robot does not stop. Drag the amber diamonds on the field to position them.
  • Code steps (S) run the instant the robot reaches that point — run inline in the step runner, so statements only, no sleep()/blocking calls (use a Wait step for those).
  • Loop code (L) — code that runs continuously from one part of the path to another: pick a from-step and a to-step, write the block, and it executes EVERY loop cycle while the robot travels between them (intake sweeps, sensor checks, arm control…). Optionally gate it to a % range of its anchor step. Covered steps show its colored bar; hover a card to see the span on the field.

4 · Robot actions & tuning

  • Volley (V) = aim the turret at an aim point, spin the flywheel to the distance-based rpm, set the hood, wait until ready, feed N balls. One step.
  • Intake (I), Shoot (F), Aim (A), Flywheel (P), Hood, Gate, Stop all are the same pieces on their own. Aim keeps tracking the point while the robot drives.
  • Everything numeric (PIDF, rpm/hood distance models, turret mapping, gate positions, shot timing, power, aim points, hardware names) is in the Tuning tab and written to class T. The shot calculator shows rpm and hood for a distance.
  • Defaults come from your TeleOp (6.22 rpm/in + 2516, hood −0.00309/in + 0.652, gate 0.5/0.7). The feed timing per ball is a starting guess — tune it.

5 · Generated OpMode — one file, one loop

  • All movement, actions, code and waits run from ONE while (opModeIsActive()) loop. Each planner step is a case in runStep(); the next starts when it returns true. stage = steps started so far.
  • Use follower, robot (e.g. robot.setIntake(1), robot.startShoot(3)), telemetry, stepTimer, P(x, y, deg) and progress() in your own code.
  • Routes become one Pedro PathChain; through steps become a chain of cubic Beziers matching the preview.

6 · Turns, waits, per-move options

  • Turns use follower.turn(...). Waits: timed or a Java condition (colorSensor.alpha() > 50).
  • Each drive step can set speed, heading mode, completion (SETTLED / LENIENT + tolerance), a timeout, and path callbacks (onStart / onProgress / onComplete).

7 · Export

  • Copy Java / Download .java gives the full OpMode. Export saves the plan + tuning as .json (also auto-saved in this browser).
